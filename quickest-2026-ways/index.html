Quickest 2026 ways to build a complete 2D/2.5D creature-catching RPG (React + PixiJS) — to 100% of its systems

Summary — read this first

Fastest licence-clean route, in one paragraph: Do not port a Pokémon game. Use the pret decomps only as a *schema checklist* (what fields a creature, move, trainer, map, song and weather system need), then fill every JSON file with original creatures, names, art and music. Build the web game as React (shell, menus, settings, save UI) + PixiJS v8 (canvas, tilemaps, sprites, battle/HUD) + a single data-driven JSON core (`species.json`, `moves.json`, `learnsets.json`, `evolutions.json`, `trainers.json`, `encounters.json`, `maps/*.tmj`, `music.json`, `backgrounds.json`). For art, start from Kenney/OpenGameArt CC0 packs and original Pixelorama/LibreSprite work, cleaned in bulk with rembg + BiRefNet (MIT), not U2-Net-by-default and not BRIA RMBG-2.0 for commercial work. For music, do not ship 2 tracks: ship a 35–45-track original soundtrack (see §5 track list) authored in LMMS/Ardour/OpenMPT/FamiStudio, rendered as gapless OGG loops with `intro + loopStart/loopEnd`, and driven at runtime by Howler.js (simple playback) + Tone.js/Web Audio (stems, bar-aligned switching) or FMOD/Wwise only if you leave the browser for a native build. For backgrounds, do not ship 8 biomes: ship one tileset *system* — primary+secondary tilesets, metatile behaviour, 3–5 render layers, palette/tint variants for morning/day/evening/night + seasons, and a weather particle/tint overlay — so 20+ towns/routes/caves/forests/beaches/mountains/cities/interiors are cheap recombinations, not 20 hand-painted backdrops.

Confidence: `index` only (search-result text, read 2026-10-25/26). No page was verified live in a research browser in this run. Licence statements below are only as strong as the cited source; always re-check the licence file of the exact pack/model/version before shipping.

Licence-clean boundary — the most important caveat in this report:

  • pret projects are publicly readable decompilations, but that does not make Pokémon names, stats, dialogue, sprites, music or ROM data free to ship. One secondary source in this research notes pret disassemblies ship no licence file, and palette tables reproduced from them are reproduced “with attribution rather than under [an] MIT grant” — i.e. reading ≠ relicensing. Treat pret as *structure reference only*: field names, state machines, file layout, loop/weather logic.
  • The same applies to PokeAPI: it is a free, no-key JSON API for Pokémon data, but its data is still Pokémon IP. Use it, if at all, only to *validate your schema* (does a species record need types/abilities/learnsets/evolutions?), then delete Pokémon values and write original ones.
  • “Licence-clean” in this report therefore means: code/tools under MIT/BSD/GPL/CC0/OFL as cited, plus your own creatures/art/music/dialogue. If a tool, model or pack is CC-BY, keep its credit file; if it is CC BY-NC (BRIA RMBG-2.0 weights), do not use its output commercially.

1b. Exact file map → neutral JSON (schema only, original values)

The pokeemerald-expansion species pipeline is the clearest worked example found: a JS builder fetches C headers and assembles structured objects, in this order — species constants → empty object → evolution (before forms) → forms → stats/abilities → learnsets → sprite data. Copy that *order*, not its values.

| Options / settings | `include/config/*.h` (battle, item, overworld, species, save toggles in expansion); `include/constants/flags.h` + `vars.h` (unused flags/vars are labelled, useful as a “settings/flags inventory” pattern) | `settings.json` + `save.json`: `{textSpeed, battleStyle, battleAnimation, sound:{music,sfx,master}, frame, language, accessibility:{reducedMotion, highContrast, colourblindPalette}}` — persist in `localStorage`/IndexedDB, never in a ROM-style save block |

| Battle (state machine) | pokeemerald battle system + Pokémon Showdown (see §2f) | `battle.json` + engine: turn order by Speed → action select → target select → resolve → win/lose check; damage/effect resolution driven by `moves.json` + `typeChart.json` |

Extraction method that stays licence-clean (do this, in this order):

1. Read the pret file list and copy *field names and types only* into your own schema doc.

2. Write a small parser (Python/Node) that reads a pret header only to prove your parser handles the syntax — e.g. the inclement-emerald-pokedex pattern of `getSpecies()/getBaseStats()/getLevelUpLearnsets()/getEvolution()` — then point the same parser at your own `.h`-style or, better, directly at your own JSON. Do not commit parsed Pokémon data.

3. Validate completeness against a checklist, not against a Pokémon dump: every species has stats, at least one ability, a learnset, an evolution entry or `evolvesTo:null`, and an encounter or trainer source; every map has a music id, a weather id and an encounter table or `encounters:null`.

4. Ship a `LICENCE.md` + `credits.json` that lists every tool/pack licence and states: “All creature names, art, music and dialogue are original or CC0/CC-BY as credited; no Nintendo/Pokémon assets are included.”

1c. What pret cannot give you

  • No web engine, no React/PixiJS code, no licence to ship its content, no modern audio (see §5: GBA M4A is a MIDI→assembly pipeline, not Web Audio).
  • DS projects (Diamond/Platinum/HeartGold/BW2) add NARC/overlay complexity with no web payoff — use them only for design ideas (day/night variants, seasons).

2a. Background removal & sprite cleanup — fastest, licence-checked

| Tool / model | Licence | Fastest at | Cannot do / trap | Maps to |

|---|---|---|---|---|

| Real-ESRGAN (xinntao) | BSD-3-Clause | 2×/4× AI upscaling of illustrations/anime (`RealESRGAN_x4plus_anime_6B` for flat art); PNG keeps transparency. | Does not invent detail (“a blurry face stays a slightly cleaner blurry face”); photo model over-smooths line art; caps at ~1 MP input in some hosted wrappers. Sprite-cleanup pipeline (fastest, in order): 1) draw/AI-generate at 2–4× final size → 2) `rembg` + BiRefNet-general → 3) alpha-matting/decontaminate pass → 4) downscale to final size with nearest (pixel art) or Lanczos (painted art) → 5) palette-quantise to your game's palette (Pixelorama/LibreSprite) → 6) manual 5-minute edge pass per hero creature, 30-second pass per common creature. AI cleanup speeds step 2; it does not replace step 6 for hero art, and it does not create a consistent art style — that comes from one palette + one outline rule applied to everything.

2e. Music — summary (full treatment in §5)

5. EXPANSION — MUSIC: a full soundtrack, not two songs

5a. How Pokémon games actually build music (decomp structure — copy the architecture, not the audio)

GBA (pokeemerald/pokefirered/pokeruby) — M4A engine:

  • Pipeline: standard MIDI files → `mid2agb` tool → `.s` assembly files containing a `SongHeader` + track data. The build does not ship MIDI; it compiles it.
  • Song table: `sound/song_table.inc` + `include/constants/songs.h` route every track/SFX to a *music player* with a priority: e.g. `MUS_DUMMY` → `MUSIC_PLAYER_BGM` (priority 0), `SE_SELECT` → `MUSIC_PLAYER_SE2` (2), `SE_BALL_OPEN` → `MUSIC_PLAYER_SE1` (1), `SE_LOW_HEALTH` → `MUSIC_PLAYER_SE3` (3). Separate players mean BGM, SFX and cries do not stomp each other.
  • Voice groups (instrument banks): `sound/voice_groups.inc` — each voice group is up to 128 entries, one per MIDI program number (entry 0 = program 0, etc.). An entry can be a DirectSound instrument (raw 8-bit signed PCM in `sound/direct_sound_samples/`), a keysplit/drumset, or a PSG (programmable sound generator) voice: square1, square2, programmable wave, noise. A “master voice group” (one bank reused by every song, plus per-song extras only where needed) is the community-recommended shortcut — copy that idea as a single shared sample/synth bank in your web game, not 40 separate banks.
  • Cries: separate system — `sound/cry_tables.inc` (`cry` macro), `gCryTable`, `gPokemonCrySongs`/`gPokemonCryMusicPlayers` so cries never interfere with BGM/SE players. Your equivalent: a dedicated SFX bus for creature cries, with per-creature pitch/variation, not a music track.
  • Looping: GBA sequences loop by jumping back to a loop point in the sequence data — the *concept* to copy is “intro (play once) + loop section (repeat forever)”, not the assembly. In web audio this is `AudioBufferSourceNode.loopStart/loopEnd` (§5d).
  • What GBA cannot do that you can: real audio files, stereo stems, dynamic layering, crossfades, reverb — all cheap in Web Audio, all expensive/impossible on GBA. Do not emulate M4A in JavaScript; emulate its *routing table* (song id → player → priority → bank) and nothing else.

DS (Diamond/Platinum/HeartGold/BW2) — sequenced audio + variants:

  • DS music is also sequence + sample-bank based (NARC archives, `songs.mk`-style references in expansion notes: delete a MIDI + its `songs.mk`/`ld_script` reference + replace its `song_table.inc` entry with `mus_dummy` to remove a track — the same “registry” pattern as GBA).
  • The DS-era *design* leap is variants, not synthesis: day/night variants (Diamond/Platinum: Twinleaf, Sandgem, Jubilife, Oreburgh, Floaroma, Eterna/Celestic, Hearthome, Solaceon/Pastoria, Veilstone, Snowpoint, Sunyshore, League, Fight Area, Valor Lakefront, Pokémon Centers, Routes 201/203/205/206/216/225/228 all change day vs night) and seasonal + movement + proximity variants (Black/White: seasons change instruments — spring basic, summer louder arrangement, autumn piano/xylophone/saxophone additions, winter chimes; moving adds tambourine/snare; nearby NPC musicians add their instruments while in earshot; low-HP “pinch” music in BW replaces the battle theme, and in Sword/Shield the gym-leader theme is dynamic by battle progress). Copy the *variant matrix*, not the tracks.

Modern Pokémon (for completeness): dynamic themes that change with battle progress (gym-leader crowd chant, etc.) — same stem/parameter idea as §5d, just with a full orchestra budget. Your web version is stems + parameters, not an orchestra.

Scale check — why “2 songs” was never enough: a Pokémon-scale game needs, by category, roughly: title (1) + intro (1) + menu/heal/shop (3) + towns/cities (8–12, one per major town, reused for small towns) + routes/fields (4–6) + caves/dungeons (3–4) + water/beach (1–2) + forest (1) + mountain/snow (1–2) + gym/dojo (1–2) + rival (1) + wild battle (1) + trainer battle (1) + gym/dojo battle (1) + evil-team battle (1) + elite/champion battle (2) + legendary battle (1) + victory (1) + defeat/game-over (1) + evolution (1) + capture (1, usually a jingle) + event/mystery (2–3) + ending/credits (1–2) + day/night/season variants (not new compositions — same composition, different stems/mix, §5d). That is 35–45 registry entries, ~25–30 unique compositions, plus jingles. §5e gives a concrete list you can actually commission/compose against.

5c. CC0 / royalty-free loop libraries — how to use them without ending up with a generic soundtrack

  • OpenGameArt CC0 collections (e.g. “CC0 Music” by OwlishMedia; “Audio – Commercial use OK” by ImogiaGames): already contain, by name, battle themes, town themes, crystal-cave tracks, menu music, loading loops, boss themes (symphonic metal, 8-bit), desert/forest ambience, victory jingles. Filter to CC0, download, keep the OGA credits file, and re-arrange: change tempo/key, re-voice with your shared instrument bank, add your motif, cut to your loop structure. A CC0 track used verbatim in 100 other games is not a soundtrack; a CC0 track *re-composed* into your game's harmonic language is a legitimate starting point.
  • itch.io packs with a real track list (use as a template for your own list, and as placeholders): Momiziba “8bit Music Pack for RPG” — 29 tracks: 3 opening/ending, 2 field, 5 battle, 3 dungeon, 3 city/town, 5 castle, 3 vehicle, 5 other (casino/shrine/church/requiem/desert), commercial use allowed, credit optional, no secondary resale; Kyoomei “8-Bit RPG Music Pack” — 10 tracks, 25–65 s loops, 3 audio channels, intro+main-loop split for first/last tracks (the exact intro+loop pattern §5d recommends); LudoLoon “Roguelike Adventure Music Pack” — castle/cave/desert/dungeon/forest/hills/ruins/sewers/town/winter + title/menu/victory/game-over/loot/treasure, full loops + individually rendered sections (186 files full / 56 essentials, ~2 h / 58 min) — the “sections” idea is exactly how you build adaptive stems. Check each pack's page before use — itch.io has no site-wide licence.
  • SubspaceAudio / Airos / qubodup CC0 collections on OGA (from the first research pass): boss battle loops, chiptune collections, menu/level loops — good for battle/jingle placeholders while original tracks are composed.

5d. How to structure and implement the soundtrack (the engineering that makes 35 tracks manageable)

Registry (one file, the web equivalent of `song_table.inc`):

{
  "id": "route_day",
  "file": "audio/music/route_day.ogg",
  "intro": 0, "loopStart": 8.0, "loopEnd": 72.0,
  "bpm": 132, "key": "C major",
  "stems": ["route_day_bass.ogg","route_day_drums.ogg","route_day_melody.ogg","route_day_harmony.ogg"],
  "variants": {"night": "route_day_night.ogg", "winter": "route_day_winter.ogg"},
  "bus": "bgm", "priority": 0, "duckOn": ["battle_start"]
}
  • Intro + loop: render every track as `intro (play once, e.g. 0–8 s) + loop section (8–72 s, repeats)`. In Web Audio set `loopStart/loopEnd` to the loop section; in Howler use a sprite or two files (intro file → on `end`, start loop file with `loop:true`). Prefer OGG over MP3 for loops (MP3 padding = audible gap even with Web Audio).
  • Loop points: compose to a bar boundary (e.g. exactly 16 bars at a fixed BPM), export with a click-free tail (reverb tail either cut cleanly or baked into the loop's start), and verify by listening to 3 consecutive loops. Use CrossLooper only for adopted CC0 tracks that lack points.
  • Vertical layering (intensity within a state): one composition, 3–5 stems at the same BPM/key, all playing in sync, stems faded in/out by game state. Canonical mapping: exploration = bass + harmony; moving = + drums (BW tambourine/snare idea); danger/boss = + brass/percussion; low HP = + pinch layer *or* switch to a pinch variant (BW's low-HP theme replaces the battle theme — a deliberate, if divisive, design choice; a subtler web version is to fade in a heartbeat/percussion stem rather than replacing the whole track). All stems share tempo/key so changes feel natural — this is the definition of vertical orchestration.
  • Horizontal re-sequencing (state changes): switch tracks only at a bar/beat boundary (Tone.js Transport scheduling, or a “pending track” that starts at the next bar), with a short crossfade (0.5–2 s) or a bridge/stinger for big changes (town → battle, battle → victory). Never hard-cut mid-bar except for jingles/stingers (which are designed to interrupt).
  • Parameters (the FMOD/Wwise idea, implemented in 50 lines of JS): `intensity` (0–1, from battle state: HP, turn count, boss phase), `exploration` (moving vs idle), `timeOfDay`, `season`, `weather`, `proximity` (nearby NPC musician volume by distance). Each parameter maps to stem gains or to a variant file. That is your entire adaptive system — no middleware required for a web game.
  • Buses & priorities (the M4A player idea, in Web Audio): `bgm` (music, ducked by battle), `sfx` (UI, battle hits, cries — separate bus so cries never duck music), `ambience` (weather/wind/water loops, per-map), `voice` (if any). Master + per-bus volume in settings; respect `prefers-reduced-motion` for visualisers, not for audio.
  • Procedural / generative layer (past the Pokémon level, cheaply): for ambient areas (caves, forests, gardens), do not compose 10 more tracks — generate them: a Tone.js chord-pad + pentatonic melody generator seeded by map id, with wind/water noise, playing under the composed stems. It is infinite, coherent (same key/tempo as the map's theme), and $0. Keep it to ambience; composed tracks carry towns/battles/story.
  • File discipline: one folder per track (`audio/music/<id>/`), stems as separate OGGs, a `music.json` registry, a `credits.json` per track (composer, licence, source), and a CI check that every `musicId` referenced by a map/trainer/battle exists and loops cleanly (duration > 0, loopStart < loopEnd, all stems same duration/BPM).

6. EXPANSION — BACKGROUNDS: a full background system, not 8 biomes

6a. How Pokémon files do backgrounds (structure — copy the system, not the art)

Tiles, metatiles, palettes (GBA pokeemerald):

  • Tile: 8×8 px, the smallest unit. A tile reference packs tile id (10 bits), X-flip, Y-flip and palette id (4 bits, 16 palettes) into 16 bits.
  • Metatile: 16×16 px, made of 4 graphical tiles *per layer*; in vanilla a metatile can only be on two of the three background layers at a time. A metatile also carries a behaviour (collision, warp-capable, encounter-generating, ledge direction, surf-only, animated door, etc.) — behaviour is gameplay, not just art, and it is the single most important field to copy into your JSON.
  • Tilesets: every map uses a primary + secondary tileset (512 metatiles each in vanilla, 1,024 total; expandable to 2,048/4,096 by repurposing bits, per pret wiki). Primary = shared terrain (grass, water, paths); secondary = map-specific (town buildings, cave walls, gym interiors). Copy this split: one shared tileset for all outdoor maps + one per biome/interior family, and your art budget collapses.
  • Porymap format (compiled): indexed `tiles.png` + `metatiles.bin` + `metatile_attributes.bin` + `palettes/` (numbered `.pal` files) + optional `anim/` folders. Porytiles format (decompiled/editable): three layer PNGs (`bottom.png`, `middle.png`, `top.png`) + `attributes.csv` + optional `palette-primers/`. For your web game the equivalent is Tiled: tileset image + `.tsx`/`.tmj` + per-tile properties (behaviour, terrain, encounter flag).
  • Map layers (GBA BG 0–3): BG0 = UI (priority 0); BG1 = top map layer (priority 1, elevations 4/6/8/10/12); BG2 = middle map layer (priority 2, elevations 1/2/3/5/7/9/11); BG3 = bottom map layer (priority 3). An NPC renders above a layer if its elevation (Z) exceeds that layer's priority — e.g. default player Z=3 is covered by the top layer but above the middle/bottom, so tree canopies and bridges correctly occlude the player. A “triple-layer metatile” modification gives full control of all three BG layers. Your PixiJS equivalent: 5 containers in fixed order (see §6b) + per-object `z`/elevation, not a single flat layer.
  • Map data: `data/maps/<Map>/map.json` (via `mapjson`), `data/layouts/layouts.json`, `data/maps/map_groups.json` — layout (size, tilesets, border), events (warps, NPCs, signs, scripts), and encounters are separate concerns in one map record. Copy that separation.
  • Animated tiles: tileset `anim/` folders (water, torches, waterfalls, flowers) — in PixiJS these are `AnimatedSprite` tiles or shader-animated tiles, driven by a per-tileset `animations.json`, not by redrawing maps.

Weather (pokeemerald, `src/field_weather.c`):

  • 18 weather values, set per map and by triggers: rain, thunderstorm, downpour, shade, fog, ash, sandstorm, drought, etc. Rain darkens scenery to about 13/16 of full light while people keep their colours; drought uses precalculated colour bins (`graphics/weather/drought/colors_n.bin`, `DROUGHT_COLOR_INDEX`) and 19-level contrast maps (`sContrastColorMaps`, `sDarkenedContrastColorMaps`) because per-palette real-time calculation was too CPU-expensive on GBA. Rain/ash particles use specialised sprite systems, not generic OAM, to save resources. Lightning uses a per-colour tint table chosen to avoid palette wrap-around (blending functions in vanilla do not clamp — a warning worth copying: always clamp your tints).
  • Your web translation: weather = (a) a particle system (rain/snow/ash/sand/leaves/petals, PixiJS `ParticleContainer` or plain sprites, pooled), (b) a tint/brightness overlay (see §6b), (c) a gameplay flag (encounter table modifier, movement modifier, battle effect flag). All three from one `weatherId` in `maps.json`. No weather = no particles + no tint, not a separate map.

Time of day (the generational split — get this right):

  • Emerald/FireRed: no time-of-day lighting. Emerald's RTC drives berries and daily events, not light; FireRed has no time system at all. If you copy Emerald alone, you get weather but no day/night.
  • Crystal (GB/GBC): the day/night reference. RTC splits the day into morning (04:00), day (10:00), night (18:00) — 6/8/10 hours. Each period has its own 8 background palettes + 8 object palettes + (outdoors) roof colours, reloaded in one frame on change, no fade. Only towns/routes + 1 cave follow the clock; 207 of 208 indoor maps are fixed at day; 27 maps (24 caves) are permanently night. Copy the *rule* (outdoors follow clock, interiors fixed, caves permanently dark) — it is a design decision, not just a palette swap.
  • Diamond/Platinum/HeartGold: day/night music + scenery variants (§5a) — same clock, applied to more systems.
  • Black/White: seasons (monthly) change scenery, music (§5a), wild encounters and events (e.g. winter snow/hail, summer beach crowds, seasonal creature forms). Copy seasons as a *fourth* variant axis, not as four copies of every map.
  • Expansion (pokeemerald-expansion) modernisation: `TIME_OF_DAY_FADE` extends GBA palette fading with a `PaletteFadeControl` (NORMAL_FADE vs TIME_OF_DAY_FADE, the latter respecting palettes immune to time-of-day, e.g. UI/glowing objects) and `Begin/UpdateTimeOfDayPaletteFade` — the exact pattern for a smooth web fade (lerp tint over 1–2 s, exempt UI/HUD/glowing tiles).

6b. The larger, better background system to build (web, 2026)

Layer stack (PixiJS, bottom → top):

1. `sky` — gradient / parallax sky image (per biome + time-of-day tint), scrolls at 0.1–0.3× camera.

2. `far` — distant hills/trees/city skyline, parallax 0.3–0.5×, tinted by time/weather.

3. `ground` — Tiled tilemap, bottom + middle layers (terrain, paths, building bases, water). Collision/behaviour from metatile properties.

4. `actors` — player, NPCs, creatures, with elevation/Z so they sort correctly against layer 5.

5. `overhead` — Tiled top layer (tree canopies, bridges, tall buildings, tall grass tops) + roof layer, drawn above actors where elevation says so.

6. `weather` — particle container (rain/snow/ash/sand) + fullscreen tint/gradient overlay (night blue, drought warm, fog white) + lightning flash (optional, with a reduced-motion/accessibility off-switch — one source explicitly omits lightning flashes for photosensitivity reasons; follow that).

7. `ui` — HUD, dialogue, menus (never tinted by time/weather — exempt, per expansion's TIME_OF_DAY_FADE rule).

Background registry (one file, the web equivalent of layouts + tilesets + palettes):

{
  "id": "route_forest",
  "tilesetPrimary": "tiles/outdoor_shared",
  "tilesetSecondary": "tiles/forest",
  "layers": ["sky","far","ground","actors","overhead","weather"],
  "palettes": {"morning": "palettes/forest_morning.json", "day": "…", "evening": "…", "night": "…"},
  "seasons": {"spring": {"overlay": "petals", "tint": "#ffffff"}, "summer": {"overlay": null}, "autumn": {"overlay": "leaves"}, "winter": {"overlay": "snow", "tilesetSecondary": "tiles/forest_snow"}},
  "weather": ["clear","rain","fog"],
  "musicId": "route_day", "encounterTableId": "route_forest_enc"
}
  • Palettes as data, not art: one tileset × 4 time palettes × 4 season tints = 16 looks from one art set. In PixiJS implement palettes as (a) `sprite.tint` / `ColorMatrixFilter` (built-in: `brightness`, `contrast`, `saturate`, `hue`, `night`, `sepia`, `colorTone`, `tint` presets; filters work on both WebGL and WebGPU, GLSL + WGSL) on the map container, *not* by redrawing tiles, and (b) for pixel-perfect palettes, a shader/lookup that remaps palette indices (the GBA way, but in a fragment shader). Prefer (a) for speed, (b) only if you need exact GBA-style palette swaps.
  • Time-of-day implementation: clock (real time or in-game time, configurable in settings) → period (morning/day/evening/night, Crystal-style boundaries or your own) → lerp tint/brightness over 1–2 s (expansion fade pattern) → swap sky/far images if needed → swap music variant if the map has one. Interiors and caves exempt (fixed palette, per Crystal rule).
  • Weather implementation: `weather.json` per weather id: `{particles:{type, count, speed, size}, tint, brightness, fogDensity, encounterModifier, battleModifier, ambienceLoop}`. Particles pooled, capped (e.g. 200 rain drops), disabled on low-power setting. Weather is per-map + per-trigger (script can set `weather:rain` for a story storm, then restore).
  • Seasons implementation: season = month (BW-style) or in-game season counter → season tint + overlay particles + tileset-secondary swap (snow roofs, autumn leaves) + music variant + encounter table variant. Four seasons × one tileset system = a visibly different world four times a year for near-zero extra art.

Background catalogue — what “larger than 8 biomes” actually means (build these as maps, not as paintings):

Towns (starting, market, port, mountain, snow, desert, capital) · Cities (large city, harbour city) · Routes (grass, forest, beach, mountain, desert, snow, swamp) · Caves (mine, crystal, ice, lava, ruins) · Forests (dense, bamboo, autumn) · Beaches/coast · Mountains/snowfields · Deserts · Swamps · Interiors (houses × variants, lab, shop, healing centre, gym/dojo × types, library, tower, hideout, castle/palace) · Special (garden, farm, harbour, bridge, volcano, sky island, underwater). That is 30+ *places* from ~10 tileset families (shared outdoor, town, forest, cave, snow, desert, beach, interior, gym, dungeon) × time/season/weather variants. The art budget is tilesets + variants, not places.

Tools for backgrounds (licence-checked):

  • Tiled (map editor, TMX/TMJ) + pixi-tiledmap (PixiJS v8 loader: TMJ/TMX parsing, no external deps, all layer types/orientations, batched rendering, runtime tile editing, procedural generation, export back to Tiled JSON, `applyParallax`, nearest-scaling for pixel art, shared texture cache). Tiled's own docs list pixi-tiledmap as the HTML5/PixiJS loader — this is the direct web replacement for Porymap.
  • Porymap / Porytiles (GBA only): use only if you are studying pret maps; do not build a web game on them. Porytiles' layer-PNG + attributes-CSV model is, however, a good mental model for how to organise your own tileset source (bottom/middle/top PNGs + attributes CSV → Tiled tileset).
  • Kenney + OpenGameArt CC0 tilesets (§2d): Kenney Tiny City (2026, 16×16, 130+ PNGs, tilemap with/without margin, CC0) for cities; free itch.io top-down sets (16×16, 129-tile forest/village set: grass/dirt/sand/cobblestone, animated water, shores, roofs/walls/doors, 11 trees, market stalls; CC0 top-down bundle: grassland, beach/water, dungeon, farm/village, each 16-tile corner autotile + Tiled `.tsx`, CC0) for the first maps. Autotiling is the speed win: a 16-tile corner autotile or 47-tile blob set means you paint terrain and edges join themselves — check for a full edge/corner set before adopting any pack, and keep tile size consistent (do not mix 16 px and 32 px art).
  • Procedural backgrounds: WFC/Markov (§3) for wild caves, post-game dungeons and garden plots; hand-design all story maps. Validate every generated map (connectivity, warp reachability, encounter-tile coverage) before shipping it.
  • Parallax & 2.5D: PixiJS `PerspectiveMesh` (v8) for pseudo-3D battle backgrounds / title pans; Tiled image layers with parallax factors for far layers; DisplacementFilter for water ripple (built-in, WebGL+WebGPU). Battle backgrounds should be *derived from the map you battled on* (BW idea: city skyline in city battles, forest in forest battles) — one `battleBackground.json` mapping `mapBiome → background layers + tint`, not 30 hand-painted battle screens.

What backgrounds cannot do: a tileset system cannot create a distinctive art direction by itself — one shared palette, one outline rule, one light direction, and one scale (16×16 or 32×32, not both) across all tilesets is what makes 30 places look like one game. Enforce that in a style guide, not in code.
